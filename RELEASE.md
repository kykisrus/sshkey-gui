# Как выпускать новую версию

Короткий чек-лист, чтобы документы не отставали от релиза.

## 1. Подготовить изменения

1. Дописать изменения в `CHANGELOG.md` — новый раздел сверху:

   ```markdown
   ## 0.6.5 — 2026-11-24

   - Что изменилось для пользователя, обычными фразами.
   - Технические детали — отдельным пунктом, если они нужны.
   ```

   Тело релиза на GitHub собирается именно из этого раздела.

2. Поднять версию в двух местах (должны совпадать):

   - `VERSION` — одна строка, например `0.6.5`;
   - `app.py` — `VERSION = "0.6.5"`.

3. Обновить версию в `README.md` в строке `**Версия:** X.Y.Z`.
   Если меняется установка — поправить и примеры команд.

4. Проверить документацию на смысл, а не только на цифры: новые возможности,
   пути к файлам, зависимости, ограничения. README — для пользователя,
   `SECURITY.md` — для тех, кто оценивает риски.

## 2. Проверить локально

```bash
bash packaging/check-docs.sh     # версии в README, CHANGELOG и коде совпадают
python3 desktop.py --selftest    # приложение поднимается и отдаёт интерфейс
bash packaging/build-deb.sh      # .deb собирается
```

Посмотреть, как будет выглядеть описание релиза:

```bash
bash packaging/release-notes.sh v0.6.5
```

## 3. Выпустить

```bash
git add -A
git commit -m "0.6.5: краткое описание изменений"
git tag -a v0.6.5 -m "Версия 0.6.5"
git push origin main --tags
```

После пуша тега GitHub Actions сам:

- собирает `.deb` для Linux и `sshkey-gui.exe` для Windows;
- берёт раздел из `CHANGELOG.md` и оформляет описание релиза;
- публикует релиз с двумя файлами.

Ничего вручную создавать не нужно. Проверить результат:

- <https://github.com/kykisrus/sshkey-gui/releases>
- вкладка Actions — оба задания должны быть зелёными.

## 4. Если что-то пошло не так

- **Тег уже отправлен, но сборка упала.** Исправляем причину, коммитим и выпускаем
  следующую версию (`0.6.6`). Перевешивать существующий тег не нужно.
- **Забыли обновить README.** `packaging/check-docs.sh` в CI упадёт и не даст
  выпустить релиз с рассинхроном версий.
- **Нужно поменять только описание релиза.** Правьте `CHANGELOG.md` и выпускайте
  следующую версию — существующее описание лучше не переписывать задним числом.
